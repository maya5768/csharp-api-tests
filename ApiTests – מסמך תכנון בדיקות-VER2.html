1מטרה והיקף

מה הפרויקט מנסה להוכיח, ומה בכוונה נשאר מחוץ לו.

מטרה

לבנות סוויטת בדיקות API ב-C# שמאמתת לא רק שה-API "עונה", אלא שהתשובה נכונה: קוד סטטוס, תוכן, ומבנה שתואם חוזה מוגדר מראש. בנוסף, להראות שהבדיקות עצמן אמינות, כלומר שהן נכשלות כשמשהו באמת שבור.

מטרה שנייה, ברמה זהה: קוד בדיקות שבנוי כמו קוד מוצר. כלומר, שכבות מופרדות, מחלקות עם אחריות אחת ושמות שמתארים בדיוק מה הן עושות, כך שהוספת endpoint או בדיקה חדשה לא מחייבת לגעת בקוד קיים (פירוט בסעיף 4).

בתוך ההיקף

  • קריאה של פוסט קיים: GET /posts/{id}
  • יצירה של פוסט: POST /posts
  • אימות קודי סטטוס, שדות חובה וערכים
  • אימות חוזה מול JSON Schema
  • בדיקה שלילית לאימות החוזה
  • תשתית קוד בשכבות (Client, Model, Validator, TestData)
  • הרצה אוטומטית ב-CI

מחוץ להיקף

  • בדיקות עומס וביצועים
  • בדיקות אבטחה והרשאות (השירות פתוח, ללא אימות משתמש)
  • עדכון ומחיקה (PUT, PATCH, DELETE), שמתוכננים כהרחבה
  • בדיקת שמירה בפועל של נתונים, כי השירות לא שומר מידע

מה נחשב הצלחה

  • כל מקרי הבדיקה עוברים מקומית וב-CI, וכל אחד מהם נראה נכשל לפחות פעם אחת כשהתנאי שלו הופר.
  • אין בגוף אף בדיקה כתובת URL, פענוח JSON ידני או יצירה של HttpClient. כל אלה נמצאים בשכבות התשתית.
  • מי שקורא רק את שמות הבדיקות ואת גוף הבדיקה מבין מה נבדק, בלי לפתוח קבצים אחרים.

2המערכת הנבדקת

על מה הבדיקות רצות, ומה חשוב לדעת על ההתנהגות שלו.

JSONPlaceholder הוא שירות REST API ציבורי וחינמי, שנבנה בדיוק לצורך בדיקות ואב-טיפוס. כתובת הבסיס: https://jsonplaceholder.typicode.com/

Endpointפעולהתשובה צפויההערה
GET /posts/1קריאת פוסט קיים200, אובייקט פוסטהנתונים קבועים, ולכן אפשר לצפות לערכים ידועים
GET /posts/99999קריאת פוסט שלא קיים404משמש בבדיקת ההרחבה
POST /postsיצירת פוסט201, הפוסט עם id חדשהשירות מדמה יצירה ולא שומר את הנתונים

מבנה של פוסט: ארבעה שדות. userId ו-id הם מספרים שלמים, ו-title ו-body הם מחרוזות.

דוגמאות תשובה

כך נראות התשובות בפועל. מהן נגזרים המודלים (סעיף 5) והסכמה (סעיף 9).

GET /posts/1 → 200

{
  "userId": 1,
  "id": 1,
  "title": "sunt aut facere repellat...",
  "body": "quia et suscipit..."
}

POST /posts → 201

{
  "title": "Test title",
  "body": "Test body",
  "userId": 1,
  "id": 101
}

השירות מחזיר את מה שנשלח, ומוסיף id חדש (תמיד 101, כי יש בו 100 פוסטים קבועים).

3גישת הבדיקות

כל תשובה נבדקת בארבע רמות, מהבסיסית לעמוקה. כל רמה תופסת סוג אחר של תקלה.

סטטוס

הקוד שחזר הוא הקוד הצפוי (200, 201, 404). תופס endpoint שבור או שגיאת שרת.

תוכן

השדות הצפויים קיימים, ובשדות שערכם ידוע הערך נכון. תופס שדה חסר או ערך שגוי.

חוזה

המבנה כולו תואם ל-JSON Schema, כולל טיפוסים. תופס שינוי מבני שלא בדקנו במפורש.

שלילית

אימות החוזה נכשל כשהקלט שבור. מוכיח שהבדיקה עצמה לא עוברת תמיד.

איפה בדיקות API בפירמידת הבדיקות

בדיקות API נותנות את היחס הטוב ביותר בין כיסוי לעלות: הן בודקות את ההתנהגות האמיתית של השירות, אבל בלי התלות בממשק משתמש שמשתנה הרבה.

עקרונות

  • תבנית AAA: כל בדיקה בנויה משלושה חלקים, Arrange (הכנה), Act (שליחת הבקשה), ו-Assert (בדיקת התוצאה). בקוד הם מסומנים בהערה.
  • בדיקה אחת, מטרה אחת: כשבדיקה נכשלת, השם שלה אומר מיד מה נשבר.
  • שמות בדיקה: לפי התבנית Action_ExpectedResult, למשל GetPost_ReturnsOk.
  • בדיקות עצמאיות: אין תלות בסדר ההרצה, ואף בדיקה לא מסתמכת על תוצאה של בדיקה אחרת.
  • הבדיקה לא יודעת HTTP: הבדיקה מבקשת "פוסט לפי מזהה", ולא בונה בקשת GET. את הפרטים מסתירה שכבת ה-Client (סעיף 4).
  • הודעת כישלון ברורה: כשאימות סכמה נכשל, רשימת השגיאות מוצגת בהודעה, כדי שלא יהיה צורך לדבג כדי להבין מה שבור.

4ארכיטקטורת הקוד

איך הקוד מאורגן, לפי איזה עיקרון, ולמה החלוקה הזו נכונה גם כשהפרויקט יגדל.

העיקרון: Page Object Model, מותאם ל-API

Page Object Model (POM) נולד בבדיקות UI: לכל עמוד באתר יש מחלקה שמסתירה את פרטי ה-HTML (selectors, כפתורים), והבדיקה קוראת לפעולה בשם עסקי, למשל loginPage.Login(user, password). אם העמוד משתנה, מעדכנים מחלקה אחת, לא עשרות בדיקות.

בבדיקות API העיקרון זהה, רק שה"עמוד" הוא משאב (resource). לכל משאב יש מחלקת Client שמסתירה את פרטי ה-HTTP: הנתיב, הפעלים, הסריאליזציה. הבדיקה קוראת ל-postsClient.GetPostByIdAsync(1), ולא יודעת שמאחורי זה יש GET posts/1. בספרות הגישה נקראת גם API Object Model או Service Object.

לפני ואחרי

לפני: מחלקה אחת עושה הכול

  • HttpClient נוצר ומוגדר בתוך מחלקת הבדיקות.
  • הבדיקה כותבת את הנתיב "posts/1" בעצמה.
  • כל בדיקה חדשה תפענח JSON בעצמה, ותשכפל קוד.
  • שינוי של כתובת, נתיב או ספרייה מחייב לעבור על כל הבדיקות.

אחרי (PR #4): שכבות עם אחריות אחת

  • תצורה במקום אחד: ApiSettings.
  • פרטי HTTP במקום אחד: PostsApiClient.
  • נתוני קלט במקום אחד: PostTestData.
  • הבדיקה מכילה רק Arrange, Act ו-Assert.

מוסכמות שמות

השם של מחלקה אומר מה התפקיד שלה, והשם של מתודה אומר מה הפעולה שהיא עושה. מי שקורא את השם לא צריך לפתוח את הקובץ.

למה זו ארכיטקטורה נכונה

  • נקודת שינוי אחת לכל סוג שינוי: כתובת אחרת → ApiSettings. נתיב אחר → PostsApiClient. שדה חדש בפוסט → Post. גרסה חדשה של JsonSchema.Net → JsonSchemaValidator. אף שינוי כזה לא נוגע בבדיקות.
  • בדיקות קריאות: גוף הבדיקה קצר כמו התיאור שלה. מה שנשאר בו הוא רק מה נבדק, לא איך מדברים עם השרת.
  • הרחבה בלי שבירה (Open/Closed): משאב חדש, למשל /comments, הוא מחלקה חדשה CommentsApiClient : ApiClientBase. שום קובץ קיים לא משתנה.
  • אין כפילות: השליחה, הסריאליזציה ויצירת ה-HttpClient כתובות פעם אחת.
  • שימוש נכון במשאבים: HttpClient אחד משותף, שמשוחרר בסוף ההרצה, במקום אחד חדש לכל בדיקה, שעלול למצות את ה-sockets.

5תיעוד המחלקות

כרטיס לכל מחלקת תשתית: מה התפקיד שלה, על מה היא אחראית, ועל מה היא בכוונה לא אחראית. מחלקת הבדיקות עצמה מתועדת בסעיף 8.

C-02

Post ו-CreatePostRequest: מודלי הנתונים

Models מומשה
Models/Post.cs · Models/CreatePostRequest.cs
תפקיד
‏Post מייצג פוסט כפי שהשרת מחזיר אותו. CreatePostRequest מייצג את מה ששולחים כדי ליצור פוסט.
אחראית על
מבנה הנתונים בלבד. System.Text.Json ממיר אותם ל-JSON ובחזרה.
לא אחראית על
שליחה, אימות או לוגיקה. אין בהם מתודות.
ממשק ציבורי
UserId, Id, Title, Body

למה שני מודלים: בבקשת יצירה אין id, כי השרת קובע אותו. מודל אחד היה שולח "id": 0, שהוא ערך שגוי. ההפרדה גם מתעדת בקוד את ההבדל בין קלט לפלט.

למה record: הוא immutable, משווה לפי ערכים, והקוד קצר. שמות המאפיינים ב-PascalCase מתורגמים אוטומטית ל-camelCase ב-JSON, כי ReadFromJsonAsync ו-PostAsJsonAsync משתמשים בהגדרות Web כברירת מחדל.

// Models/Post.cs

public sealed record Post(int UserId, int Id, string Title, string Body);

// Models/CreatePostRequest.cs
namespace ApiTests.Models;

public sealed record CreatePostRequest(int UserId, string Title, string Body);
C-03

ApiClientBase: מחלקת בסיס לכל ה-Clients

טעינה פעם אחת: בבדיקות, המופע נשמר בשדה static readonly. כך הסכמה נטענת ונרשמת פעם אחת לכל ההרצה, ולא בכל בדיקה.

הקוד 
// Validation/SchemaValidationResult.cs
namespace ApiTests.Validation;

public sealed record SchemaValidationResult(bool IsValid, IReadOnlyList<string> Errors);

// Validation/JsonSchemaValidator.cs
using System.Text.Json;
using Json.Schema;

namespace ApiTests.Validation;

public sealed class JsonSchemaValidator
{
    private static readonly EvaluationOptions Options = new() { OutputFormat = OutputFormat.List };
    private readonly JsonSchema _schema;

    public JsonSchemaValidator(string schemaFileName)
    {
        string schemaPath = Path.Combine(AppContext.BaseDirectory, "Schemas", schemaFileName);
        _schema = JsonSchema.FromFile(schemaPath);
    }

    public SchemaValidationResult Validate(string json)
    {
        using JsonDocument document = JsonDocument.Parse(json);
        EvaluationResults results = _schema.Evaluate(document.RootElement, Options);

        List<string> errors = (results.Details ?? [])
            .Prepend(results)
            .Where(node => node.Errors is not null)
            .SelectMany(node => node.Errors!.Values)
            .ToList();

        return new SchemaValidationResult(results.IsValid, errors);
    }
}

9חוזה JSON Schema

הקובץ Schemas/post.schema.json מגדיר מהו פוסט תקין. הוא משמש את TC-03 ואת TC-04, דרך JsonSchemaValidator.

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["userId", "id", "title", "body"],
  "properties": {
    "userId": { "type": "integer" },
    "id":     { "type": "integer" },
    "title":  { "type": "string" },
    "body":   { "type": "string" }
  }
}
חלק בסכמהמשמעות
$schemaגרסת התקן של JSON Schema שהקובץ כתוב לפיו (2020-12).
"type": "object"התשובה חייבת להיות אובייקט, ולא מערך או ערך בודד.
requiredרשימת שדות החובה. אם אחד מהם חסר, האימות נכשל. זה מה ש-TC-04 בודק.
propertiesהטיפוס של כל שדה: integer למספר שלם, ו-string למחרוזת.

למה אין "additionalProperties": false: ההגדרה הזו הייתה מכשילה את הבדיקה בכל פעם שהשרת מוסיף שדה חדש. הוספת שדה היא שינוי תואם-לאחור, שלא שובר אף צרכן, ולכן היא לא סיבה לכישלון. הסכמה נועלת את מה שצרכנים מסתמכים עליו, ולא יותר.

הקובץ נמצא בתיקייה Schemas/, ומוגדר ב-ApiTests.csproj להעתקה לתיקיית הפלט. JsonSchemaValidator מחפש אותו שם, דרך AppContext.BaseDirectory:

<ItemGroup>
  <None Update="Schemas\post.schema.json" CopyToOutputDirectory="PreserveNewest" />
</ItemGroup>

name: tests

16הרחבות אפשריות

כיווני המשך, לפי סדר העדיפות, ואיפה כל אחד נכנס בארכיטקטורה.
