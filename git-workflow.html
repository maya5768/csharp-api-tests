Git Workflow

שיטת העבודה עם Git בפרויקט

Feature Branch + Pull Request + Squash Merge — ומה זה אומר בפועל כשעובדים לבד.

למה בכלל תהליך מסודר, ולא פשוט push ל-main

אפשר לעבוד ישירות על main ולדחוף כל שינוי — זה עובד, אבל ההיסטוריה שמתקבלת היא בלגן של commits כמו "fix", "wip", "עוד תיקון". מי שמגיע לריפו (בודק קוד, מראיין, או אני עצמי בעוד חצי שנה) לא מבין מתוך ה-log מה קרה ולמה. תהליך מבוסס branch + Pull Request פותר את זה: כל שינוי מתועד כיחידה שלמה והגיונית, עם כותרת ותיאור, לפני שהוא נכנס ל-main.

העיקרון: Feature Branch

כל יחידת עבודה — בדיקה חדשה, תיקון, שינוי מבנה — מתבצעת ב-branch נפרד שנוצר מתוך main, ולא נכנסת ל-main ישירות. ה-branch נסגר (merge) רק כששיהיה שהוא עובד ונבדק.

מוסכמת שמות ל-branches

קידומתמתי משתמשים
test/...הוספת בדיקה אוטומטית חדשה — למשל test/get-post-returns-ok
feature/...פיצ'ר חדש / הרחבת תשתית הבדיקות
fix/...תיקון באג או בדיקה שבורה
docs/...עדכון תיעוד בלבד (README וכד')

השם עצמו צריך לתאר מה נעשה, כדי שאפשר יהיה להבין את התוכן בלי לפתוח קוד.

התהליך צעד-אחר-צעד

  1. פתיחת branch מתוך main

    git checkout -b test/get-post-returns-ok — נקודת ההתחלה תמיד main עדכני.

  2. עבודה ו-commits על ה-branch

    אפשר לעשות כמה commits קטנים תוך כדי העבודה (גם "commits ביניים") — זה לא משנה את main בכלל, וה-squash בסוף ינקה אותם.

  3. דחיפת ה-branch ל-GitHub

    git push -u origin test/get-post-returns-ok

  4. פתיחת Pull Request

    מ-branch אל main, עם כותרת קצרה ותיאור: מה נוסף/שונה ולמה. ה-PR הוא גם תיעוד לעתיד.

  5. Self-review

    בפרויקט סולו אין מי שיאשר עבורך — אז את עוברת בעצמך על ה-diff בתצוגת ה-PR (לא בעורך). רואים משם דברים שקל לפספס תוך כדי כתיבה.

  6. Squash and Merge

    GitHub דוחס את כל ה-commits מה-branch ל-commit אחד נקי על main, עם ההודעה שתכתבי (אפשר לערוך אותה לפני האישור הסופי).

  7. Delete branch

    אחרי המיזוג, מוחקים את ה-branch (GitHub מציע את זה בכפתור אחד) — הוא כבר מוזג לתוך main.

מה זה בעצם Squash Merge?

זו אפשרות מיזוג ב-GitHub (ובפקודת git רגילה: git merge --squash) שלוקחת את כל ה-commits שנצברו ב-branch, ודוחסת אותם ל-commit יחיד שנכנס ל-main — בלי לשמור את ההיסטוריה הפנימית של ה-branch. זה בדיוק מה שקורה בשלב 6 ברשימה שלמעלה.

לפני ואחרי

נניח שעבדת על test/get-post-returns-ok ויצרת שם 4 commits תוך כדי העבודה:

a1b2c3d  wip: מתחיל לכתוב את הבדיקה
e4f5g6h  fix typo
i7j8k9l  מוסיף עוד assert
m0n1o2p  cleanup

עם Squash merge, ב-main זה נכנס כ-commit יחיד, עם ההודעה שאת כותבת (או עורכת) בזמן המיזוג:

q1r2s3t  Add GetPost_ReturnsOk test

ה-4 commits המקוריים "נעלמים" מ-main — הם עדיין קיימים ב-branch, עד שהוא נמחק בשלב הבא.

שלוש אפשרויות מיזוג ב-GitHub

אפשרותמה קורה ל-main
Merge commitשומר את כל ה-commits כפי שהם, ומוסיף גם commit מיזוג נפרד — ה-log מתמלא ב"רעש" של ניסוי וטעייה
Rebase and mergeשומר את כל ה-commits המקוריים (לא דוחס), רק מעתיק אותם לקצה main בלי commit מיזוג נוסף
Squash and mergeדוחס הכל ל-commit אחד נקי — האפשרות שנבחרה לפרויקט הזה

הבחירה ב-Squash נותנת את ההיסטוריה הכי נקייה ב-main: commit אחד = feature אחד שלם ועובד, בדיוק מה שמי שסוקר את ה-log (כולל מראיין) רוצה לראות — בלי "wip" ו-"fix typo" באמצע.

מה עם אישור PR בפרויקט סולו?

אין Reviewer חיצוני — וזה בסדר. את ממלאת את שני התפקידים: פותחת את ה-PR וגם מאשרת/ממזגת אותו בעצמך. לא מגדירים ב-GitHub דרישת אישור חובה (branch protection), כי כבעלת הריפו היחידה לא תוכלי לאשר את ה-PR של עצמך — זה פשוט ייתקע.

מה שכן שווה את זה: תהליך ה-PR מכריח סקירה עצמית לפני מיזוג, ומראה בריאיון שאת מכירה את שיטת העבודה הצוותית המקובלת — גם כשעובדים לבד. תוספת שמחליפה חלק מתפקיד ה-reviewer: הרצת dotnet test אוטומטית על כל PR באמצעות GitHub Actions, כך שה-PR "ירוק" רק אם הבדיקות עוברות.

דוגמה מהפרויקט הזה

כך יושם התהליך בפועל, צעד אחר צעד:

שלבמה נעשה
1Commit ראשון על main: scaffolding בלבד — .csproj, .gitignore, README.md, README.html
2נפתח branch בשם test/get-post-returns-ok
3נוסף אליו PostApiTests.cs עם הבדיקה GetPost_ReturnsOk
4ה-branch נדחף ל-GitHub ונפתח עליו Pull Request
5Self-review על ה-diff, ואז Squash and Merge לתוך main

כל בדיקה חדשה שתתווסף בהמשך (למשל בדיקות שליליות, אימות JSON Schema) תעבור באותו תהליך בדיוק — branch משלה, PR משלה.
