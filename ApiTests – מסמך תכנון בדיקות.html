1מטרה והיקף

מה הפרויקט מנסה להוכיח, ומה בכוונה נשאר מחוץ לו.

מטרה

לבנות סוויטת בדיקות API ב-C# שמאמתת לא רק שה-API "עונה", אלא שהתשובה נכונה: קוד סטטוס, תוכן, ומבנה שתואם חוזה מוגדר מראש. בנוסף, להראות שהבדיקות עצמן אמינות, כלומר שהן נכשלות כשמשהו באמת שבור.

בתוך ההיקף

  • קריאה של פוסט קיים: GET /posts/{id}
  • יצירה של פוסט: POST /posts
  • אימות קודי סטטוס, שדות חובה וערכים
  • אימות חוזה מול JSON Schema
  • בדיקה שלילית לאימות החוזה
  • הרצה אוטומטית ב-CI

מחוץ להיקף

  • בדיקות עומס וביצועים
  • בדיקות אבטחה והרשאות (השירות פתוח, ללא אימות משתמש)
  • עדכון ומחיקה (PUT, PATCH, DELETE), שמתוכננים כהרחבה
  • בדיקת שמירה בפועל של נתונים, כי השירות לא שומר מידע

2המערכת הנבדקת

על מה הבדיקות רצות, ומה חשוב לדעת על ההתנהגות שלו.

JSONPlaceholder הוא שירות REST API ציבורי וחינמי, שנבנה בדיוק לצורך בדיקות ואב-טיפוס. כתובת הבסיס: https://jsonplaceholder.typicode.com/

Endpointפעולהתשובה צפויההערה
GET /posts/1קריאת פוסט קיים200, אובייקט פוסטהנתונים קבועים, ולכן אפשר לצפות לערכים ידועים
GET /posts/99999קריאת פוסט שלא קיים404משמש בבדיקת ההרחבה
POST /postsיצירת פוסט201, הפוסט עם id חדשהשירות מדמה יצירה ולא שומר את הנתונים

מבנה של פוסט: ארבעה שדות. userId ו-id הם מספרים שלמים, ו-title ו-body הם מחרוזות.

3גישת הבדיקות

כל תשובה נבדקת בארבע רמות, מהבסיסית לעמוקה. כל רמה תופסת סוג אחר של תקלה.

סטטוס

הקוד שחזר הוא הקוד הצפוי (200, 201, 404). תופס endpoint שבור או שגיאת שרת.

תוכן

השדות הצפויים קיימים, ובשדות שערכם ידוע הערך נכון. תופס שדה חסר או ערך שגוי.

חוזה

המבנה כולו תואם ל-JSON Schema, כולל טיפוסים. תופס שינוי מבני שלא בדקנו במפורש.

שלילית

אימות החוזה נכשל כשהקלט שבור. מוכיח שהבדיקה עצמה לא עוברת תמיד.

עקרונות

  • תבנית AAA: כל בדיקה בנויה משלושה חלקים, Arrange (הכנה), Act (שליחת הבקשה), ו-Assert (בדיקת התוצאה).
  • בדיקה אחת, מטרה אחת: כשבדיקה נכשלת, השם שלה אומר מיד מה נשבר.
  • שמות בדיקה: לפי התבנית Action_ExpectedResult, למשל GetPost_ReturnsOk.
  • בדיקות עצמאיות: אין תלות בסדר ההרצה, ואף בדיקה לא מסתמכת על תוצאה של בדיקה אחרת.

6מקרי הבדיקה

פירוט מלא של כל בדיקה: מה נשלח, מה בודקים, ולמה הבדיקה קיימת. כל הבדיקות נמצאות במחלקה PostApiTests.

TC-01

קריאת פוסט קיים מחזירה 200

חיובית מומשה
GetPost_ReturnsOk()
מטרה
לוודא שה-endpoint זמין ומחזיר תשובה מוצלחת לבקשה תקינה. זו בדיקת ה-happy path הבסיסית.
בקשה
GET/posts/1
שלבים
  1. שליחת GET ל-posts/1 עם ה-HttpClient המשותף.
  2. קריאת קוד הסטטוס מהתשובה.
תוצאה צפויה
קוד סטטוס 200 OK.
Assert
Assert.Equal(HttpStatusCode.OK, response.StatusCode)
בדיקת אמינות
להריץ פעם אחת עם ערך צפוי שגוי (NotFound), ולוודא שהבדיקה נכשלת עם הודעה ברורה שמציגה Expected ו-Actual. מבוצע לפני המיזוג ל-main.
הקוד 
[Fact]
public async Task GetPost_ReturnsOk()
{
    // Act
    HttpResponseMessage response = await client.GetAsync("posts/1");

    // Assert
    Assert.Equal(HttpStatusCode.OK, response.StatusCode);
}
TC-02

פוסט מכיל את שדות החובה עם ערכים נכונים

חיובית מתוכננת
GetPost_ContainsRequiredFields()
מטרה
לוודא שהתשובה לא רק "הצליחה", אלא מכילה את המידע הנכון.
בקשה
GET/posts/1
שלבים
  1. שליחת GET ל-posts/1.
  2. קריאת גוף התשובה כמחרוזת ופענוח שלו כ-JSON עם JsonDocument.
  3. בדיקה של כל שדה חובה.
תוצאה צפויה
קיימים ארבעה שדות: userId, id, title, body. הערך של id הוא 1, כמו שביקשנו, ו-title אינו ריק.
Assert
‏Assert.True(root.TryGetProperty(...)) לכל שדה, ו-Assert.Equal(1, id).

למה לבדוק את id: בדיקה שמוודאת רק שהשדה קיים תעבור גם אם השרת החזיר פוסט אחר. בדיקת הערך מוודאת שקיבלנו בדיוק את מה שביקשנו.

כיוון למימוש 
string json = await response.Content.ReadAsStringAsync();
using JsonDocument doc = JsonDocument.Parse(json);   // using System.Text.Json;
JsonElement root = doc.RootElement;

Assert.True(root.TryGetProperty("title", out _));
Assert.Equal(1, root.GetProperty("id").GetInt32());
TC-03

פוסט תואם לחוזה (JSON Schema)

חוזה מתוכננת
GetPost_MatchesSchema()
מטרה
לוודא שמבנה התשובה כולו תואם להגדרה: שדות החובה קיימים, ולכל שדה יש את הטיפוס הנכון.
בקשה
GET/posts/1
קלט נוסף
קובץ הסכמה post.schema.json (פירוט בסעיף 7).
שלבים
  1. טעינת הסכמה מהקובץ.
  2. שליחת GET ל-posts/1 וקריאת התשובה.
  3. אימות התשובה מול הסכמה עם JsonSchema.Net.
תוצאה צפויה
תוצאת האימות תקינה (Valid).

ההבדל מ-TC-02: ‏TC-02 בודק שדות שבחרנו לבדוק. הסכמה בודקת את כל המבנה, כולל טיפוסים. למשל, אם id יחזור פתאום כמחרוזת "1" במקום מספר, TC-03 יתפוס את זה. זה נקרא Contract Testing.

הערת מימוש: קוד האימות ייכתב לפי התיעוד של JsonSchema.Net בגרסה 9.4.0, כי הממשק שלה משתנה בין גרסאות. בנוסף, צריך להגדיר ב-.csproj שהקובץ post.schema.json יועתק לתיקיית הפלט, אחרת הבדיקה לא תמצא אותו בזמן ריצה.

TC-04

פוסט בלי שדה חובה נכשל באימות החוזה

שלילית מתוכננת
PostMissingTitle_FailsSchema()
מטרה
להוכיח שאימות החוזה באמת תופס תשובה שבורה, ולא עובר תמיד.
בקשה
LOCALno network call
הבדיקה לא פונה ל-API. היא בודקת את מנגנון האימות עצמו, על JSON שנבנה בקוד.

למה זה חשוב: אם הסכמה הוגדרה לא נכון, למשל בלי required, ‏TC-03 עדיין יעבור, ואף אחד לא יידע שהאימות לא עושה כלום. ‏TC-04 סוגר את הפער הזה.

TC-05

יצירת פוסט מחזירה 201 ואת הנתונים שנשלחו

חיובית מתוכננת
CreatePost_ReturnsCreated()
מטרה
לוודא שיצירת משאב חדש מחזירה את קוד הסטטוס הנכון, ושהשרת קיבל את הנתונים כפי שנשלחו.
בקשה
POST/posts

שלבים

7חוזה JSON Schema

הקובץ post.schema.json מגדיר מהו פוסט תקין. הוא משמש את TC-03 ואת TC-04.

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["userId", "id", "title", "body"],
  "properties": {
    "userId": { "type": "integer" },
    "id":     { "type": "integer" },
    "title":  { "type": "string" },
    "body":   { "type": "string" }
  }
}
חלק בסכמהמשמעות
$schemaגרסת התקן של JSON Schema שהקובץ כתוב לפיו (2020-12).
"type": "object"התשובה חייבת להיות אובייקט, ולא מערך או ערך בודד.
requiredרשימת שדות החובה. אם אחד מהם חסר, האימות נכשל. זה מה ש-TC-04 בודק.
propertiesהטיפוס של כל שדה: integer למספר שלם, ו-string למחרוזת.

כדי שהבדיקה תמצא את הקובץ בזמן ריצה, הוא מוגדר ב-ApiTests.csproj להעתקה לתיקיית הפלט:

<ItemGroup>
  <None Update="post.schema.json" CopyToOutputDirectory="PreserveNewest" />
</ItemGroup>

8נתוני בדיקה

מאיפה מגיעים הנתונים, ולמה הם בטוחים לפרסום.

  • נתונים מהשירות: פוסט מספר 1 של JSONPlaceholder. הנתונים קבועים ולא משתנים בין הרצות, ולכן אפשר לצפות לערכים ידועים.
  • נתונים שנבנים בקוד: הפוסט החדש ב-TC-05 והפוסט השבור ב-TC-04. שניהם בדויים לחלוטין.
  • מדיניות: אין בפרויקט נתונים, קוד או סכמות ממערכות אמיתיות. כל הנתונים ציבוריים או בדויים, ולכן הריפו יכול להיות ציבורי.

  • בדיקות מבוססות נתונים: ‏[Theory] עם [InlineData], כדי להריץ את TC-02 על כמה מזהי פוסט בלי לשכפל קוד.

  • API משלי: שירות קטן ב-ASP.NET Core עם SQL Server, שבו אפשר לבדוק גם שמירה בפועל.
  • בדיקות UI: ‏Playwright for .NET באותו פרויקט.
  • קונטיינר: הרצת הסוויטה ב-Docker, כדי שהסביבה תהיה זהה בכל מחשב.
